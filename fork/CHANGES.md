# Fork changes

Every change this fork carries on top of upstream, one line each:
commit subject, why, and related upstream issues and PRs.
`git log --no-merges upstream-main..main` lists the commits, including
follow-ups and reverts. Include issue links even when no PR exists yet; a related
issue may cover more than the fork's fix. Keep each entry on a single line;
the sync script deletes the line of a change whose upstream PR merged. Closing
an issue alone does not revert a patch. See `fork/README.md` for how to add or drop
an entry.

Issue: https://github.com/pingdotgg/t3code/issues/23403. PR: https://github.com/pingdotgg/t3code/pull/23420

- `fix(server): Claude takes agent updates at tool boundaries`: agent updates to a busy Claude turn wait in the durable queue (the upstream PR's rule) and the running turn takes them at its next root PostToolBatch or Stop hook, with no timer; unclaimed updates start the next turn. Agent promotions of queued text follow the same rule; human promotions stay native. Held queues and stopped runs refuse the claim, so Stop wins. Updates with attachments steer natively with a note that they came from another agent. Human steering, explicit restarts and other providers are unchanged. See [delivery limits and mobile follow-ups](INSTALL.md#claude-follow-ups-during-a-running-turn). Offered upstream on top of the maintainer's takeover. Issue: https://github.com/pingdotgg/t3code/issues/21895. Related PR: https://github.com/pingdotgg/t3code/pull/21158

- `feat(server): skip cache writes on cold Claude compaction`: opt-in Claude setting **Skip cache writes on cold compaction** runs a compaction of a thread whose prompt cache has expired (by the TTL Claude reported for its latest turn; unknown keeps caching) and whose Claude process was already released, without prompt caching, so the history the summary replaces is not cached again; the next message reopens Claude with caching (one extra process start). Saves usage only if every gateway or proxy forwards requests without cache markers unchanged; the compaction sends `X-CPA-Prompt-Cache-Mode: explicit` for a CLIProxyAPI build that honors it. Issue: https://github.com/pingdotgg/t3code/discussions/18069 (was https://github.com/pingdotgg/t3code/issues/18067). PR: none yet
- `feat(server): retry Codex turns that fail on model capacity`: when a Codex root turn (including a delegated task's) fails on capacity (`serverOverloaded`), throttling (`rateLimitExceeded`), a server error, or a transport failure Codex stopped retrying (`responseTooManyFailedAttempts`, `httpConnectionFailed` and the response-stream codes, unless the HTTP status is a client error other than 408/429), the run stays open and continues with empty-input turns until one makes progress, waiting 10s and doubling up to a 3-minute cap with no attempt limit (each wait is drawn from the upper half of its step, so threads that failed together do not retry in lockstep), including when Codex rejects a retry start as overloaded (JSON-RPC -32001); progress restarts the backoff. A `usageLimitExceeded` with no upcoming reset time rechecks the same way, while one with a known reset still waits for limit recovery. Throttling and 429 exhaustion are no longer classified as usage limits, so a stale quota snapshot cannot schedule reset-based resumes (reverses upstream PR 17501's classification). The retry row counts down and Stop cancels it. When the failed turn's subagents are still running, the retry waits for them to finish, and Stop in the meantime ends them and settles the run. Issues: https://github.com/pingdotgg/t3code/issues/12826 (closed), https://github.com/pingdotgg/t3code/issues/24885 and https://github.com/pingdotgg/t3code/issues/17503. PR: none yet

Squash of danielyc's PR, adapted to the fork's settings and docs. Issue: none linked. PR: https://github.com/pingdotgg/t3code/pull/17618
