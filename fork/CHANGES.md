# Fork changes

Every change this fork carries on top of upstream, one line per feature or fix:
its original commit subject, why, and related upstream issues and PRs.
`git log --no-merges upstream-main..main` lists the commits, including
follow-ups and reverts. Follow-ups rewrite their change's line instead of
adding one; see _Adding a change_ in `fork/README.md` for the exception.
Include issue links even when no PR exists yet; a related issue may cover more
than the fork's fix. Keep each entry on a single line; the sync script deletes
the line of a change whose upstream PR merged. Closing an issue alone does not
revert a patch. See `fork/README.md` for how to add or drop an entry.

- `feat(claude): compact only idle threads that will resume`: **Compact idle threads** defaults to **Before the cache expires** in the fork, and before the cache expires an idle Claude thread compacts by how likely it is to be reused, each group with its own switch and minimum context size under **Settings → Providers → Advanced**: **waiting threads** (60K) have a watched PR (even after CI finishes) or issue, awaited subagent or background work, a scheduled task targeting it (including enabled, unblocked webhooks), a still-asking machine link, a pending question answerable by message, a pending guest message, or an active proposed plan, and count as waiting even when settled; **open threads** (150K) are other unsettled threads; **settled threads** (500K, off by default) are settled, and their idle compaction keeps them settled instead of unsettling them like other messages. A switched-off group never compacts its threads; with all three off nothing compacts before the cache expires unless a thread asks, though the **Compact** chip still offers it when you return. The defaults come from measured returns on one machine's history: unsettled threads idle past an hour got a human reply about half the time at 150K and above, above the roughly 18-25% that pays for a compaction there, while no late return to a settled thread was observable (reopening erases the settle time), so settled compaction is off by default and starts at 500K, where a roughly 10% return rate breaks even, for anyone who turns it on. A pending question answerable by message also allows tier and one-shot compaction; live requests, approvals and active runs still block it. **Compact snoozed threads** (default on, shown when the global choice or any Claude provider override compacts before the cache expires) lets snoozed threads compact and counts the snooze end as a wake; any scheduled task or snooze ending before expiry skips compaction because the cache is still warm. The wire keeps the mode plus `idleCompactionWaiting`, `idleCompactionOpen` and `idleCompactionSettled` objects (`enabled`, `minTokens`; patches merge per field), because shipped clients reject unknown idle compaction modes; servers without them hide the group rows, and a provider override of **Before the cache expires** uses the same groups. Threads get **Compact before cache expires** (follow settings, this time only, always, never) in web, desktop and mobile thread menus and through `t3_thread_configure`. **Always** and **This time only** compact from the waiting minimum regardless of the group switches. **This time only** (`"once"`) stores `compactOnceRequestedAt` and compacts after the current turn if nobody replies before the cache expires, then returns to the thread's choice: it applies like **Always** in any mode but **Never** (including **When you return**) until any run starts after it, so nothing clears it; setting null, true or false removes it, a thread set to **Never** refuses it, and shells report it as `compactOnce` (older servers omit it and hide the choice). Agents are told to use it when ending a turn that waits on the user with a large context. `t3_thread_send` with `contextPolicy: "compact"` to the caller's own busy thread queues the compaction after the current turn instead of refusing. Compaction turns no longer claim queued agent messages at Claude hook boundaries, so reports start the next turn. Older servers hide the thread control. Opt-in **Skip cache writes on cold compaction** runs a compaction of a thread whose prompt cache has expired (by the TTL Claude reported for its latest turn; unknown keeps caching) and whose Claude process was already released, without prompt caching, so the history the summary replaces is not cached again; the next message reopens Claude with caching (one extra process start). It saves usage only if every gateway or proxy forwards requests without cache markers unchanged; the compaction sends `X-CPA-Prompt-Cache-Mode: explicit` for a CLIProxyAPI build that honors it. Issue: https://github.com/pingdotgg/t3code/discussions/18069 (cache writes; was https://github.com/pingdotgg/t3code/issues/18067). PR: none yet

- `feat(claude): questions wait between a minimum and a maximum`: a Claude `AskUserQuestion` no longer holds its turn open indefinitely. It waits at least 5 minutes and at most 60, and the maximum stays a minute short of the prompt cache's expiry (measured from the request that asked, using the TTL the session last reported, assumed to be 1 hour when none was reported), so the request that follows still reads the cache. A shorter cache window lowers the minimum to that maximum (a 5-minute TTL waits about 4 minutes), and a cache that already expired before the question appeared leaves only the 60-minute limit. A person's message that is delivered during the turn ends the wait at once. An agent's or the system's message (another thread's `t3_thread_send`, a delegate report) ends it once the minimum has passed. Queued messages and scheduled tasks still wait for the turn to end. Without an answer, Claude is told how long it waited and why it stopped (the user, the agent in a named thread, or the time limit), and is asked to continue with independent work or end its turn. The question card stays open and is answered later by a message, so an idle thread with that question counts as **waiting** for idle compaction. Answers, Stop and the resume-compaction prompt are unchanged. A pending update that would turn a question answerable by message is dropped if the question was already answered. Known limit: an answer submitted within milliseconds of the deadline can miss Claude and show as not delivered. The limits are hidden Claude provider settings, `questionMinWaitMinutes` and `questionMaxWaitMinutes`, set in `settings.json`. Issues: https://github.com/pingdotgg/t3code/issues/15517 and https://github.com/pingdotgg/t3code/issues/26841. Related PR: https://github.com/pingdotgg/t3code/pull/26868 (closed). PR: none yet
